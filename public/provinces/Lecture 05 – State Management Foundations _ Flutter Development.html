Concept

Concept Overview: What Is State?

  • State = data that can change and affects the UI
  • UI is a function of state: UI = f(state)
  • Every build() call re-renders from current state
  • Wrong state management → inconsistent, buggy UIs
  • Right pattern choice depends on scope and complexity

Lifecycle

StatefulWidget: The Full Lifecycle

  • createState() — called once; creates the State object
  • initState() — first setup; never in the constructor
  • build() — re-runs on every setState() call
  • didUpdateWidget() — parent passes new configuration
  • dispose() — always clean up to prevent memory leaks

Lifecycle

Lifecycle Methods in Practice

class _TimerWidgetState
    extends State<TimerWidget> {
  late Timer _timer;
  int _seconds = 0;

  @override
  void initState() {
    super.initState(); // always first
    // Start here — not in constructor
    _timer = Timer.periodic(
      const Duration(seconds: 1),
      (_) => setState(() => _seconds++),
    );
  }

  @override
  void dispose() {
    _timer.cancel(); // always clean up!
    super.dispose(); // always last
  }

  @override
  Widget build(BuildContext context) =>
      Text('Elapsed: $_seconds s');
}

Key Rules

  • Initialize controllers in initState()
  • super.initState() must come first
  • super.dispose() must come last
  • late keyword defers initialization safely
  • Cancel every timer / subscription in dispose()

setState

setState(): How It Works

// ✅ CORRECT — mutate inside setState
setState(() {
  _count++;
  _label = 'Updated';
});

// ❌ WRONG — mutate before setState
_count++;
setState(() {}); // bad practice

// ❌ WRONG — async without mounted check
Future<void> fetchData() async {
  final data = await api.load();
  if (!mounted) return; // ← guard!
  setState(() => _items = data);
}

Rules

  • Schedules a rebuild of this widget only
  • Always mutate state inside the callback
  • Check mounted before calling after any await
  • Never call inside dispose()
  • Runs synchronously before the next frame

setState

When setState Is Not Enough

  • Data needed by a sibling widget → lift state up
  • Data needed by many distant widgets → use Provider
  • Data that persists across navigation → app-level state
  • Data fetched asynchronously from an API → async patterns
💡 Rule: state lives in the lowest common ancestor of all widgets that need it.

Pattern

Lifting State Up: Pattern

class _ParentWidgetState
    extends State<ParentWidget> {
  int _count = 0;

  void _increment() =>
      setState(() => _count++);

  @override
  Widget build(BuildContext context) =>
    Column(
      children: [
        // data flows DOWN
        DisplayWidget(count: _count),
        // events flow UP
        IncrementButton(
          onPressed: _increment,
        ),
      ],
    );
}

The Pattern

  • Parent state flows down via parameters
  • Events flow up via callbacks
  • Children become StatelessWidget
  • Easy to test and reuse
  • Use VoidCallback for simple events

  const IncrementButton(

  Widget build(BuildContext context) =>

Benefits

  • Stateless children = easy to unit test
  • No BuildContext dependency on state
  • Reusable across multiple screens
  • Predictable, deterministic behavior
  • Clear single responsibility

Problem

Problem: Prop Drilling

⚠️ Each intermediate widget carries props it doesn't use. Adding a layer breaks the entire chain.
  • Passing data through many layers = prop drilling
  • Fragile: intermediate widgets don't use the data
  • Hard to refactor — every layer must be updated
  • Cognitive overhead for every code reader
  • Solution: Provider for clean, scalable state sharing

Provider

ChangeNotifier: The Core of Provider

class CartModel extends ChangeNotifier {
  final List<String> _items = [];

  List<String> get items =>
      List.unmodifiable(_items);
  int get count => _items.length;

  void add(String item) {
    _items.add(item);
    notifyListeners(); // triggers rebuild
  }

  void remove(String item) {
    _items.remove(item);
    notifyListeners();
  }
}

Best Practices

  • Call notifyListeners() when data changes
  • Subscribed widgets rebuild automatically
  • Keep business logic in the model
  • Keep UI logic in widgets
  • Expose immutable getters to prevent outside mutation

Workflow

Architecture Workflow: Provider Setup

  • context.watch<T>() — subscribe to changes, triggers rebuild
  • context.read<T>() — read once, no subscription
  • context.select<T, R>() — rebuild only on a specific field change

Registering Provider in main()

void main() {

    // Provide CartModel to the whole app
    ChangeNotifierProvider(
      create: (_) => CartModel(),
      child: const MyApp(),
    ),

class MyApp extends StatelessWidget {
  const MyApp({super.key});

  @override
  Widget build(BuildContext context) =>
    MaterialApp(
      title: 'Flutter Shop',
      home: const ShopScreen(),
    );
}

Setup Notes

  • Wrap as high as needed — not always at root
  • create lambda is lazy — runs on first access
  • Use MultiProvider for multiple models
  • Can scope to a single route for isolation
  • dispose() on the model is called automatically

Practice A: Reactive Counter with Lifting State

Goal: Build a 2-widget counter — a display and 3 action buttons via a shared parent.

class CounterScreen extends StatefulWidget {
  const CounterScreen({super.key});
  @override
  State<CounterScreen> createState() => _CounterScreenState();
}

class _CounterScreenState extends State<CounterScreen> {
  int _value = 0;

  @override
  Widget build(BuildContext context) => Scaffold(
    appBar: AppBar(title: const Text('Reactive Counter')),
    body: Column(
      mainAxisAlignment: MainAxisAlignment.center,
      children: [
        CounterDisplay(value: _value),
        CounterControls(
          onIncrement: () => setState(() => _value++),
          onDecrement: () => setState(() => _value--),
          onReset:     () => setState(() => _value = 0),
        ),
      ],
    ),
  );
}

Practice A

Practice A: Answer / Walkthrough

  • _CounterScreenState owns _value — single source of truth
  • CounterDisplay reads but never modifies state
  • CounterControls fires callbacks — zero state ownership
  • All children are StatelessWidget → easy to unit test
  • Extracting widgets keeps build() clean and readable
If you find yourself passing the same value through 3+ widget layers, that's a signal to consider Provider for that piece of state.

Practice B

Practice B: Provider-Powered Shopping Cart

Goal: Add items from a product list; view cart count in the AppBar via Consumer.

class ShopScreen extends StatelessWidget {
  const ShopScreen({super.key});
  static const _products =
      ['Headphones', 'Keyboard', 'Mouse', 'Monitor'];

  @override
  Widget build(BuildContext context) => Scaffold(
    appBar: AppBar(
      title: const Text('Shop'),
      actions: [
        // Consumer rebuilds only the badge
        Consumer<CartModel>(
          builder: (_, cart, __) => Badge(
            label: Text('${cart.count}'),
            child: const Icon(Icons.shopping_cart),
          ),
        ),
      ],
    ),
    body: ListView.separated(
      itemCount: _products.length,
      separatorBuilder: (_, __) => const Divider(),
      itemBuilder: (ctx, i) => ProductTile(name: _products[i]),
    ),
  );
}

Practice B

Practice B: ProductTile Widget

class ProductTile extends StatelessWidget {
  final String name;
  const ProductTile(
      {super.key, required this.name});

  @override
  Widget build(BuildContext context) {
    // read() — no rebuild needed here
    final cart = context.read<CartModel>();

    return ListTile(
      title: Text(name),
      trailing: ElevatedButton(
        onPressed: () {
          cart.add(name);
          ScaffoldMessenger.of(context)
            .showSnackBar(SnackBar(
              content: Text('$name added'),
            ));
        },
        child: const Text('Add'),
      ),
    );
  }
}

watch vs read

  • context.read in a button callback — ✅
  • context.watch in build() — ✅
  • Consumer wraps only the badge → minimal rebuilds
  • Never use context.watch in callbacks or initState

Practice B

Practice B: Answer / Walkthrough

  • CartModel holds cart logic separate from UI
  • Consumer wraps only the badge — minimal rebuilds
  • context.read in event handlers avoids unnecessary subscriptions
  • ChangeNotifierProvider at root — any screen can access the cart
  • This pattern scales to real checkout flows with multiple screens
Never call context.watch inside callbacks or initState — it only works correctly during build(). Doing so will throw a runtime error or produce unpredictable rebuilds.

Summary

State Fundamentals

  • State = data that changes and affects UI
  • Use setState for local widget state
  • Lift up when siblings share the same state
  • Respect lifecycle: initState → build → dispose

Provider Pattern

  • ChangeNotifier + notifyListeners()
  • watch in build(), read in callbacks
  • select for precision rebuilds
  • Minimal rebuild surface = better performance & fewer bugs

"Manage state well, and your UI takes care of itself."
